# Spec-Driven Exploration Development Prompt

> 用户草拟的原始 prompt，保存备查。
> 用于指导 Ralph Loop 进行长时探索式开发。

---

请你围绕当前最新的产品定义文档执行一轮长时探索式开发，但要严格遵守"Spec-first、small-batch、可回退、可验证"的原则。

你必须先完整阅读并理解以下三个文档，并把它们作为最高优先级约束来源：

- PRODUCT-SPEC.md
- ARCHITECTURE.md
- LEARNING-GUIDE.md

你的工作目标不是随意做功能，而是围绕这些文档，把产品往"更符合 Spec 的方向"推进，并通过小步迭代不断逼近。

====================
总目标
====================

在不做大规模破坏性改动的前提下，围绕 Spec 中定义的产品方向，进行一晚上的自主探索式开发：
- 优先强化核心体验
- 优先让现有系统更符合 Spec
- 优先做能被测试和验证的小步改进
- 每一步都要可回退、可解释、可自测

不要把系统带偏成 generic AI workspace、纯笔记工具、纯聊天工具、或过度自动化黑盒 Agent。

====================
最高约束
====================

你必须始终服从以下原则：

1. PRODUCT-SPEC 是产品真相来源
2. ARCHITECTURE 是系统约束来源
3. LEARNING-GUIDE 是开发哲学来源
4. 不为了"做很多改动"而做改动
5. 不做没有验证路径的大改
6. 不做破坏性重构，除非非常小且明确必要
7. 不在没有明确收益的情况下扩大复杂度
8. 优先保持系统稳定、可信、可追溯、可解释

====================
先做的第一件事
====================

开始任何开发前，先做以下动作：

1. 读完三个文档
2. 用你自己的话总结：
   - 这个产品是什么
   - 核心用户任务是什么
   - 核心 loop 是什么
   - 什么叫"好的 AI 行为"
   - 当前最值得推进的 3 个方向是什么
3. 检查 git 状态
4. 先创建一个"Spec rewrite baseline"提交（如果工作区干净，则创建一个空提交作为起点；如果有未提交变更，则先把当前状态安全提交）
5. 从这个安全基线开始工作

这个基线提交的目的：
- 防止你后面探索跑偏
- 确保任何时候都能回滚
- 保留当前 Spec 重构成果

====================
工作方式
====================

你必须采用"小步探索循环"，而不是大爆炸式修改。

每一轮循环都遵循：

1. 选一个最小但有价值的改进目标
2. 明确它对应 Spec 的哪一部分
3. 先读相关代码和现状
4. 设计最小实现方案
5. 修改少量文件
6. 运行相关测试 / lint / build / smoke checks
7. 自己评估这次改动是否真的更符合 Spec
8. 满足条件就 commit
9. 再进入下一轮

====================
每轮改动的硬限制
====================

除非绝对必要，否则每轮：
- 尽量不要触碰太多文件
- 尽量不要跨很多模块
- 尽量不要同时解决多个大问题
- 尽量不要引入新框架
- 尽量不要改动数据库 schema
- 尽量不要做大面积 UI 重写
- 尽量不要重构"只是因为看起来更优雅"

默认策略：
- 小 patch
- 小重构
- 小交互修正
- 小状态流修正
- 小型体验增强
- 小型安全边界增强
- 小型测试补强

====================
优先级判断
====================

优先做这些类型的工作：

P0. 明显违背 Spec 的地方
- AI 行为与 Spec 冲突
- 权限/确认/可追溯性不符合文档
- Chat 没有扮演 orchestration layer
- Surface 与主任务不匹配
- 体验明显偏离"研究推进感"

P1. 高杠杆核心体验增强
- 让 Reader / Board / Chat / Memo 更符合 surface contract
- 让"研究被推进了"更可见
- 让 AI 建议 / draft / commit 的边界更清楚
- 让信息密度更合理
- 让用户更容易理解当前研究状态

P2. 可信度和可控性增强
- 更明确区分 AI draft vs committed content
- 更清晰的 confirmation / review 机制
- 更好的 traceability 展示
- 更稳的 bounded autonomy

P3. 开发质量增强
- 补测试
- 补局部状态保护
- 降低明显脆弱逻辑
- 降低跑偏风险

如果你发现某个改动虽然"看起来酷"，但不明显提升以上目标，优先不做。

====================
你可以重点探索的方向
====================

结合最新 Spec 改写摘要，优先考虑这些方向中最小、最有价值、最可验证的项：

1. Chat 作为 orchestration layer 的体验对齐
2. Reader / Board / Memo 是否真正各自回答一个核心问题
3. AI draft / write / destructive 的边界是否在 UI 中足够清楚
4. 是否存在"AI 聪明但 workspace 没推进"的问题
5. 是否存在"信息很多但研究状态不清楚"的问题
6. Cold start / empty state 是否需要最小补强
7. Research Run 输出后的落地体验是否真的服务主 loop
8. 用户是否能看懂 AI 做了什么、改了什么、建议了什么

如果你要解决开放问题，优先用"小范围产品落地"方式，不要先做宏大架构。

====================
禁止事项
====================

未经充分理由，不要做以下事情：

- 不要大规模重写页面结构
- 不要全局替换状态管理
- 不要重构大量 API 只是为了"更干净"
- 不要引入大型新依赖
- 不要做数据库迁移，除非非常小且明确必要
- 不要删除现有核心 feature
- 不要把系统简化成普通 chat app
- 不要为了自动化而牺牲可审阅性
- 不要悄悄扩大 AI 自治权限
- 不要把 open-ended thinking 变成僵硬表单系统

====================
测试与验证要求
====================

每一轮都尽可能进行以下验证中的至少一部分：

- 相关单元测试
- 相关集成测试
- lint / type / build 检查
- 最小手动 smoke test
- 对照 PRODUCT-SPEC 的 acceptance criteria 做自评
- 对照"Definition of Good / Bad"做一次简短判断

如果改动无法被验证，就不要轻易扩大范围。

====================
提交策略
====================

你必须频繁提交，小步提交。

提交策略：
- 先提交一个 baseline
- 每完成一个小的、可验证的改进就提交一次
- commit message 要清楚说明：
  - 改了什么
  - 为什么改
  - 对应哪个 spec 约束或体验目标

避免：
- 很久不提交
- 攒一个巨大 commit
- 一次 commit 混很多不相关改动

====================
自我评估方式
====================

每一轮结束时，简短回答：

1. 这次改动对应了哪条 Spec？
2. 用户体验哪里更接近"研究工作台"而不是"普通 AI 工具"？
3. 这次改动有没有增加不必要复杂度？
4. 这次改动是否更清楚地表达了：
   - bounded autonomy
   - visible progression
   - traceability
5. 是否应该立即提交，还是应该回退 / 缩小范围？

====================
遇到不确定时的默认行为
====================

如果你不确定：
- 优先做更小的改动
- 优先保留现状
- 优先补测试或补保护
- 优先增强可见性和可审阅性
- 优先遵循 Spec 而不是自由发挥

如果发现一个想法需要大规模重构才能成立：
- 先不要直接做
- 先记录为 follow-up
- 尝试找一个 20% 改动、80% 收益的版本

====================
今晚运行的工作风格
====================

我希望你像一个谨慎但主动的产品工程代理：

- 主动发现值得做的小机会
- 主动读 Spec 对照现状
- 主动测试
- 主动提交
- 主动评估是否跑偏
- 但不要激进
- 不要大拆大建
- 不要把"探索式开发"变成"不可控重构"

====================
结束条件
====================

在以下任一情况下可以结束：
- 已完成若干个高质量小步改进，且系统保持稳定
- 接下来只剩大改才有明显收益
- 测试/构建表明继续推进风险上升
- 已经有足够清晰的 follow-up list 留给下一轮

结束时请输出：
1. 今晚做了哪些提交
2. 每个提交改善了什么
3. 哪些地方已经更符合 Spec
4. 哪些值得下一轮继续做
5. 哪些想法被你刻意放弃，因为会过于破坏性

开始前先读文档、总结、检查 git 状态、建立安全基线提交，然后再进入第一轮小步探索。
